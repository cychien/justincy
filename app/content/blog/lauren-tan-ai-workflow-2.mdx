上一篇講到，Lauren 一個月能推 2000 個 PR，靠的是她對 AI 的信任。這份信任要照順序建立：先建立規範，然後調整，最後建立驗證標準。

接下來三篇，我們照這個順序拆解她實際在用的 [pstack](https://github.com/cursor/plugins/tree/main/pstack)，看每一步怎麼落地。這篇先談建立規範。

## pstack

pstack 是一套工程工作流大全，裡面有 51 個 skill，包含 23 種常見工作流，加起來近六十萬字元。它是一個 Cursor plugin，但也能當一般 skill 使用。

內容很多，這篇只探討一件事：規範怎麼建，才會好用、有效，又方便擴展

## 建立規範

所謂規範，就是一組 skill。pstack 把 skill 分成 3 層，每層只管自己的事：

- 總機：聽懂你要什麼，交給對的 playbook
- playbook：一類任務的 SOP，也就是前面說的 23 種工作流
- 共用工具：每本 playbook 都能呼叫的專門能力

### 總機

skill 一多，我們很難全部記得，也不一定知道哪個最適合眼前的任務。總機認得每一本 playbook，替我們決定這次用哪一本，或讓幾本一起合作。

#### 解決事情的入口

pstack 的總機是 `/poteto-mode`。你只要跟它說話，不用指定 playbook，講清楚目標和怎樣算完成就好。

pstack guide 裡的例子：

```text
/poteto-mode 昨天部署之後，匯出的 CSV 少了最後一列。
失敗的 job id 是 4812。先重現，再修。
完成的標準是 6 萬列的測試資料每一列都有匯出。
給我看修正前後的列數。
```

這段 prompt 有**目標** (匯出的 CSV 少了最後一列)、**線索** (失敗的 job id)、**限制** (先重現再修)、**完成條件** (6 萬列的測試資料全部匯出)，以及要看的**證據** (修正前後的列數)。至於實際要怎麼做，交給總機決定。

#### 通用規則

通用規則是記錄在總機裡，要求每段工作流程都要遵守的原則。pstack 的通用規則包括：

自主權

```
- 直接動手，MCP 工具隨你用。改得回來的事，還有發團隊訊息、更新 ticket、跑 eval 這類對外動作，都不用先問。
...
```

核心工程原則

```
- Laziness Protocol: 要重構、要決定改動多大，或忍不住想多加一層抽象、把參數一路往下傳的時候用。能刪就刪，只做解決問題需要的最小改動。
...
```

如何回覆

```
- 用短的直述句。一句只講一件事，用句號結尾。
- 簡短不代表可以省內容。句子要短，但 playbook 要求回報的每一項都要寫到：細節、取捨、做了哪些選擇、還有哪些等你決定。
...
```

#### 意圖對應 playbook

總機最重要的工作，是判斷哪種意圖該交給哪本 playbook。以 pstack 為例：

```
- Investigation: 只問不改的問題。X 怎麼運作、Y 當初為什麼這樣做、Z 真的沒問題嗎、該選 X 還是 Y。
- Bug fix: 有人回報的 bug。先重現，找出真正的原因，再用實際跑起來的結果證明修好了。
- Perf issue: 已經量到的慢。追出原因，改完拿數字和改之前比。
- Feature: 新增或改變功能。先定好資料長什麼樣子，再從那裡開始寫。
- Refactoring: 只改結構、不改行為 (改名、抽出、內聯、去重、搬移)。
- Prototype: 用完就丟的草稿。用最省事的方式決定設計或行為；兩條路都行、試一下就知道哪條好時，直接做出來看，不用問人 (「做個 prototype」、「先 mock 一個出來」、「做個草稿來決定」)。
- Babysit: 把一個或一疊 PR 顧到可以 merge：解衝突、回 review、讓 CI 過。
- Autonomous run: 要一路做到完成、中途不停的長任務 (「做到完成為止」、「/loop 直到 X」)。
- Opening a PR: 其他每本 playbook 做完，最後都走這本。
```

#### 如何使用 playbook

在總機裡，必須明確定義如何使用配對到的 playbook，例如 pstack 是這樣定義的：

```
開一個 todolist。最前面放配對到的 playbook 步驟，一字不改地抄過來，排在這次任務自己的 todo 前面。決定不做的步驟不要刪，留在清單上，寫一行 skip: <理由>。
```

逐字複製，agent 就不會自作聰明，悄悄省掉它覺得不重要的步驟。

#### 特例：figure-it-out

有些任務太大，或根本沒有現成的 playbook，這時交給一本特別的 playbook：`figure-it-out`。pstack 是這樣寫的：

```
很大或牽涉很多地方的工作 (例如要改很多呼叫點的 migration、分很多部分的大改動)，或使用者會先離開、之後才回來檢查的工作，交給 figure-it-out。找不到合適的 playbook 時，也交給 figure-it-out。它會替這個任務量身寫一本夠嚴謹的 playbook。
```

pstack README 裡有一個例子：

```text
/poteto-mode 我要離開一陣子。
把每個呼叫同步 store 的地方，都改成新的非同步 store，
行為要完全一樣。
我回來時，要能放心這些都改對了。
```

假設 repo 裡有 40 個呼叫點。`figure-it-out` 不會直接開始改，而是先替這次任務寫出一本 playbook：

1. 訂完成條件，而且要能判斷對錯
2. 先準備好驗證
3. 拆成小單位，風險最高的先做

總歸來看，一個好的總機必須：

- 定義通用規則，讓每本 playbook 都有基本品質
- 寫清楚哪種意圖交給哪本 playbook
- 規定如何使用 playbook
- 準備 `figure-it-out`，接手太大或沒有現成 playbook 的任務

### Playbook

總機決定走哪條路，playbook 決定怎麼走。pstack 的 playbook 大多只有 10 到 25 行，以 `Bug fix` 為例 (略有刪減)：

```
### Bug fix

你擁有這個任務。規劃、審查、驗證。把調查和修正交給 sub agent，自己保持主導。

要科學。每一行出貨的 code 都要追溯到執行時的證據。「可能有幫助」的保險措施只是假設，不是修正，不能出貨。證據推翻一個假設時，把它促成的改動還原。只出貨證據支持的最小改動，不多做。

1. 在對應的介面上親自重現。只有在介面真的碰不到目標、而且已經盡力操作之後，才可以說明具體原因，請使用者重現。
2. 用二分法找原因。先列出候選假設，再逐一排除到只剩一個。用 how 看懂受影響的子系統、用 why 查回歸的歷史，替假設打底。程式狀態不清楚時，加上 log 或 instrumentation，在執行中讀它。不要猜。
3. 規劃修法。如果跨越函式邊界，先用 architect。把實作交給 sub agent，範圍要具體。
4. 在同一個介面上驗證。原本的重現步驟現在要通過。「無法判斷」或在錯的介面上驗證都不算通過，要標出來。unit test 只能證明分支的行為，不能證明 bug 不存在。
5. 安排 commit 順序，讓會失敗的重現排在修正之前。
6. 執行 Opening a PR。

回覆：壞了什麼、根本原因、怎麼修、怎麼驗證的。原封不動貼上修正前失敗、修正後通過的重現輸出。
```

從這本 playbook 可以看出幾個寫法。

- **禁止這類任務最常見的偷懶。** 修 bug 最常見的偷懶，是加幾行防禦性 code 就收工。`Bug fix` 開頭就說，這種保險措施不是修正，不能 ship。
- **用步驟，不用長篇敘述。** 步驟相比於長篇論述，agent 更知道怎麼遵守。
- **專門的能力交給共用工具。** 步驟裡只寫「用 `how`」、「用 `architect`」，怎麼做由其他 skill 負責。
- **寫清楚和相鄰 playbook 的邊界。** `Refactoring` 寫明，它不是加行為的 `Feature`，也不是修行為的 `Bug fix`。重構途中發現 bug 或缺少的功能，要拆出去另外處理。
- **結尾規定回報內容。** 每本 playbook 的最後一行都是 Reply，定義任務完成後，要輸出哪些內容。

playbook 之間也能互相呼叫。會改 code 的 `Bug fix`、`Feature`、`Refactoring`，最後一步都是 `Opening a PR`。

playbook 也能調整原則的優先順序。 例如 `Prototype` 開頭寫著：

```
唯一一本 Laziness Protocol 的「最小改動」和驗證標準反過來的 playbook。速度優先於精緻，code 品質不重要，不做規劃。
```

總歸來看，一本好的 playbook 必須：

- 開頭講清楚 agent 負責什麼
- 點名這類任務最常見的偷懶，並禁止它
- 以步驟代替冗長敘述
- 需要專門能力時呼叫共用工具，不在 playbook 裡重寫
- 寫明和相鄰 playbook 的邊界
- 結尾規定回報要包含什麼

### 共用工具

在 pstack 裡另一個重要角色是共用工具。

它們是 playbook 步驟常會呼叫的可重複使用的 skill。它們就像程式裡的 utils：

- `how`：看懂一個子系統怎麼運作。
- `why`：查某段 code 為什麼長這樣，會去翻 git 紀錄、issue、Slack 和錯誤追蹤系統。
- `architect`：寫 code 之前，先把型別、函式簽名和模組邊界設計好。
- `arena`：同一題交給幾個 sub agent 各做一份，選出最好的一份當基底，再把其他份的優點嫁接進來。
- `swarm`：把一件大工作切成互不重疊的幾份，平行處理，最後彙整成一份報告。
- `interrogate`：讓不同的 model 對同一份 diff 做對抗式 review。

對於共用工具，pstack 有幾個值得學的做法。

- **一個工具只做一件事，再互相組合。** `architect` 自己不探索 code，而是先跑 `how` 和 `why` 打底，再用 `arena` 產出幾份設計來比較。
- **輸出的形狀固定。** `how` 的報告固定分成 Overview、Key Concepts、How It Works、Where Things Live、Gotchas 五段。`interrogate` 把每個發現分進「要處理」、「可以考慮」、「知道就好」、「駁回」四類。`swarm` 的每個 worker 只能回報 PASS、ISSUES 或 BLOCKED。呼叫它的 playbook 知道會拿到什麼，就能直接接著用，例如 `Investigation` 的第 3 步，就是直接交出 `how` 格式的報告。
- **把 sub agent 的協作方式做成工具。** `arena` 讓幾個 sub agent 各做一份再挑最好的，`swarm` 讓它們分頭平行處理，`interrogate` 讓不同 model 互相審查。三者都靠多個 sub agent 加深探索的深度和品質。這些流程定義一次，任何 skill 都能直接呼叫，做到更複雜的事。

總歸來看，好的共用工具必須：

- 只負責一件事，可以單獨呼叫，也可以被其他工具組合
- 輸出固定的格式，讓呼叫它的 playbook 能接著用
- 把常用的 sub agent 協作方式做成工具，例如 `arena`、`swarm`

## 三層架構

pstack 的三層架構，讓你像寫程式一樣組織 skill：總機是 main function，playbook 是一般的 function，共用工具是 utils。每一層只管一件事，所以 skill 好擴展、好維護，agent 也好讀。

不過規範不會一次就寫對。agent 總會在你沒想到的地方出錯。下一篇我們看 pstack 怎麼把調整規範這件事，也做成 skill。
