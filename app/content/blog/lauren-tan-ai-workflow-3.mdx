規範訂好之後，下一步是磨合。agent 的產量一大，這件事光靠人手動做會跟不上，所以 pstack 把它做成幾個 skill，各自處理一種教訓。

## 一次任務的教訓：/reflect

一個任務做完，覺得過程不順時，可以跑：

```text
/reflect 這次花太久了。
把學到的東西記下來，下次不要再犯。
```

`/reflect` 會開三個 reviewer 讀這次的對話紀錄，各從一個角度找教訓：

- Judgement：找出某個具體事件背後的長期原則。
- Tooling：指出之後的 agent 不寫下來就得重新摸索的具體 tool、指令、路徑或 flag。
- Divergent：專找前兩個會漏掉的盲點。

舉個例子：你請 agent 補一個 e2e 測試，它卡在登入頁，來回問了你好幾次測試帳號。其實帳號就寫在 `.env.example` 裡。Tooling reviewer 會抓出這點，提議在 skill 裡加一句：「e2e 測試的帳號在 `.env.example`，自己去讀，不要問人。」

接著由一個 synthesizer 逐條審查這些建議。它的審查標準寫得很具體 (節錄)：

```
- Durability：路徑、SHA、工具版本和 code 的形狀都變了之後，是否仍然成立。
- Specificity：範圍夠廣，能套用到不同任務；又夠精確，讓未來的 agent 認得出什麼時候該用。
- Decision-changing：未來的 agent 會因為這次修改而做不同的事
- Structural-mechanism：如果 lint、script、metadata flag 或 runtime check 已經能強制這條規則，或能便宜地做到，就移到 Backlog。skill 的文字只留給機制無法強制的事。
- Already-covered：如果提案與現有 skill 重複，就駁回，因為問題出在執行，不在 skill。
```

synthesizer 最後把建議分成三類：接受、拒絕、待辦。針對接受的建議做調整。

## 反覆出現的錯：/correct

你一定遇過這種情況：同一個錯，你糾正了 agent 三次、五次，下一次它還是會犯。一個例子是：repo 規定資料庫操作都要經過 repository layer，例如用 `userRepository.findById(id)` 拿使用者，但 agent 老是直接 import database client 寫查詢。你在 review 裡糾正了一次又一次，換一個 agent，它又犯。

這時再多寫一條 rule 通常沒用。`/correct` 的做法是改 repo、lint、或寫腳本，讓 agent 沒機會再犯。它把修法排了優先順序：

| 修法 (由強到弱) | 效果 |
| --- | --- |
| 架構 | 錯誤不可能發生，例如把 database client 藏起來，直接 import 就失敗 |
| 型別、lint、CI | 寫錯就編譯不過或 CI 變紅，錯誤訊息直接告訴 agent 該改用哪個函式 |
| 測試 | 寫錯會被抓到 |
| 文件、rule、skill | 留給需要判斷的事 |

套到這個例子：最強的修法是不再 export database client，repository 以外的檔案根本 import 不到。做不到的話，就加一條 lint，repository 以外的檔案一 import database client 就報錯，錯誤訊息寫著「請改用 `userRepository`」。

rule 排在最後，因為 rule 的約束力是最低的。

有些判斷天生沒辦法寫成 lint，skill 是它們唯一能做的約束。能機械化檢查的教訓，就從文字移到 repo 的結構裡。

---

**和 `/reflect` 差在哪？** `/reflect` 讀的是一次對話，`/correct` 讀的是 repo 的歷史，像 commit、revert、review 留言，找出至少發生過兩次的錯。但他們都會優先考慮訂立硬性規則做規範，真的不行，才會選擇去改 skill。

## 怎麼知道改對了：eval

對於調整 skill，還有一個問題：改了之後，你怎麼知道 agent 真的會照做？

pstack guide 說：「只根據一次失敗寫出的修正，往往只對那一次有效。改過很多次之後，skill 會慢慢偏離原本的樣子。」eval 的工作，是在修改留下來之前把這種偏離抓出來。

pstack 的 eval 流程特別有趣：

1. 主 agent 會針對 skill 修改出一個題目、設置環境和 prompt，並預先訂立評分標準。
2. 主 agent 會開不同 models 的數個 sub agent 來進行測試，過程中不會告訴他們正在進行測試，為的是防止 observer effect：agent 知道自己在被測試時，表現會不一樣。
3. sub agent 都完成後，主 agent 開另一個與自己不同 model 的 sub agent 來做 review。會給它評分標準、各 model 的思考流程與產出 (去識別化)。
4. 主 agent 自己也會同步評分，最後將結果與 review agent 的相比，如果意見一致，就回報結果。如果不一致，就代表題目出的不好，再重新跑一輪。

我自己用下來，最大的改變是對 skill 的更動更有信心。

我甚至會用 eval 讓 skill 不停自我修改，直到評分通過，整個過程我完全不用管 skill 寫了什麼。

其實到最後，會發現 skill 是寫給 agent 看的，假如某個 skill 能讓不同 model 都做到想要的事，那作為人，又何必要求 skill 是怎麼寫的呢？

## 紀錄自我習慣：/automate-me

poteto-mode 寫的是 Lauren 自己的工作習慣。`/automate-me` 讓你從自己的習慣出發，產出一份屬於你的 `<你的名字>-mode`。

你不用描述自己的風格。它會派幾個 sub agent 分頭讀你最近幾週的對話紀錄，找出反覆出現的偏好：回覆的長短、怎麼派工、怎樣才算做完、commit 和 PR 的習慣。只在一段紀錄裡出現的偏好通常會被丟掉，在兩段以上都出現的才會寫進 skill。接著它會問你幾題選擇題，補上紀錄裡看不出來的意圖。

之後習慣變了，再跑一次就好。它只讀上次修改之後的對話，保留你沒推翻的規則，只修改有新證據的部分。

## 四個機制

四個機制處理的教訓不同，做的卻是同一件事：**每次糾正 agent，都把這次的教訓變成下一次會自動擋下錯誤的東西**。能寫成檢查的，就寫成檢查。需要判斷的，寫進 skill，再用 eval 確認 agent 真的照做。

想開始的話，不用一次把整套搬過來。guide 的建議是「從比你想的更小的地方開始」。先照平常的方式下 prompt，觀察 agent 在哪裡失敗。同一個錯出現第二次，就替它加一個 rule，或加一個檢查。

另外也可以反過來，完全不先定義 skill，直接請 agent 做和調整，直到一件事完全做好後，再利用 `/reflect` 請它歸結出 skill。

不過磨合得再好，agent 還是會犯錯。下一篇我們看最後一步：pstack 怎麼建立驗證標準，又怎麼把「建立驗證標準」這件事本身做成一個 skill。
