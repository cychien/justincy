調整讓 agent 產出越來越可靠，但有時它還是會犯錯，所以最後一步是建立驗證標準。

在過去，驗證與測試通常是最慢的一步，因為它在等人。不處理驗證，開再多 agent，也只是多出一堆等你 review 的東西。

第一篇提到，Lauren 列了 5 種驗證，其中後三種是軟性檢查，做法是請 agent 根據你訂好的 rule，做出一份 verification skill。這篇就來看 pstack 怎麼把這件事做出來。

這篇分三部分：

- 怎樣是好的驗證
- 什麼時候驗，以及怎麼確保真的驗了
- 怎麼替每個專案產生一份自己的驗證 skill

## 怎樣是好的驗證

### 驗證真正的成果

pstack 的原則 Prove It Works 這樣寫：

```
直接檢查真正的東西，驗證每個任務的產出。不要從替代指標、自我回報或「能編譯」去推論。

- 直接檢查 process 是否還活著，不要從衍生的狀態間接推論。
- 讀真正的值，不要讀快取或衍生出來的表示。
- 驗證失敗時，先懷疑觀察的方法，再懷疑系統。
```

build 通過、agent 說它做完了、測試全綠，都是替代指標。unit test 只能證明某個分支的行為，不能證明 bug 消失了。真正的證明，是回到使用者遇到 bug 的那個介面，重現原本的問題並解決。

guide 也列出不同的修改該怎麼驗證：

- 改 CLI，就跑真正的指令。
- 改 UI，就在執行中的 app 裡走一遍改過的流程。
- 改 parser 或 migration，就重播一份存下來的輸入。
- 改效能，就比對前後的 profile。
- 改儲存邏輯，就把寫進去的值讀出來。

### 數字也要驗證

效能改善的數字特別容易出錯。剛好有 cache、一邊用了 debug build、測試裡根本沒跑到真正的工作，都可能做出一個漂亮的數字。

所以回報任何量測數字之前，pstack 會用 `/benchmark-checklist` 問七個問題，每題都要拿實際跑出來的證據回答：

```
1. 為什麼不是兩倍？說出限制這個數字的是什麼。
2. 有沒有調校？每一邊都要用正式環境的方式跑。
3. 有沒有突破物理極限，例如磁碟頻寬或核心數？
4. 有沒有出錯，或回傳錯的結果？
5. 能不能重現？交替跑很多次，給出中位數和範圍。
6. 端到端有差嗎？在使用者真正等待的那條路徑上量。
7. 工作真的發生了嗎？確認它真的在計時範圍裡執行。
```

### 驗證的人不能是寫 code 的人

要把一串 PR merge 進去時，`Shipping` playbook 會開一個新的 sub agent 做驗證，並記下每次驗證對應的是哪一版 PR 內容。PR 被 rebase 之後內容變了，之前的驗證就不算數，要重新驗證。

這和人類團隊做 code review 是同一個道理：自己檢查自己，很難看到盲點。

總歸來看，一個好的驗證標準必須：

- 檢查真正的成果，不接受 build 通過、測試全綠這類替代指標
- 量到的數字要說得出限制在哪，並排除它量到別的東西
- 由沒寫 code 的 agent 下判定，而且判定只對它驗過的那一版有效

## 把驗證排進流程

有了標準，下一個問題是什麼時候驗。pstack 會把驗證方式在剛開始就訂好，並在做的過程中一步一步驗。

### 先訂驗證方式

如 `Autonomous run` playbook 所說：

```
在第一次迭代之前，把結束條件寫成可以檢查的判斷式 (測試全綠、重現修好了、N 個 PR 都 merge 了、pixel diff 為零)。
```

### 一步一驗

如原則 Sequence Work into Verifiable Units 這樣寫：

```
把工作排成一連串小單位，每個單位都結束在一個可以檢查的狀態，目前這個沒變綠之前不往下走。
```

一步一驗的目的是為了提早發現問題，精准定位。

總歸來看，好的驗證流程必須：

- 動手前先寫下能判斷對錯的完成條件
- 每個小單位做完就驗，綠了才往下

## 把建立驗證標準做成 skill

### 「驗證一下」沒有那麼簡單

要 agent 驗證有一個前提：agent 必須知道怎麼操作你的 app。

「驗證一下」聽起來簡單，但 agent 要怎麼打開你的 app、點哪裡、看到什麼才算成功？每次都重新摸索的話，驗證就會很隨便，每個 agent 驗的方式也都不一樣。

所以 pstack 把「替一個專案建立驗證標準」這件事本身做成 skill：`/create-verification-skill`。**它是一個產生 skill 的 skill**。在專案裡跑一次，它會讀完 repo，產生一份這個專案專用的驗證 skill，放在 `.cursor/skills/verify-<app>/`。

這份產出是寫給誰看的，skill 一開頭就講清楚了：「讀它的，會是一個做到一半、從沒看過這個 app 的 agent。」所以每一步都要寫到這樣的 agent 照著做就能完成。

### 先問 repo，再問人

產生之前，它先從 codebase 回答五個問題：

- 介面：使用者實際碰的是什麼？網頁、CLI、桌面 app、API，還是 library？
- 啟動：在本機怎麼把 app 跑起來？要哪些 port、環境變數、測試資料、登入？
- 操作：agent 能用什麼方式操作它？先找 repo 裡現成的工具，例如既有的 Playwright 測試，找不到才用通用做法。
- 觀察：能留下哪些證據？截圖、終端機輸出、API 回應、log、資料庫狀態。
- 隔離：能不能同時開兩個 instance？不行的話，驗證 skill 要寫明。寧可拒絕操作，也不能動到使用者正在用的那一個。

只有 code 裡看不出來的，才問你。如果專案現在根本跑不起來，要先修好，或精確回報問題。

### 產出：一份驗證 skill

產生出來的 `verify-<app>` 有五個段落，每段都要用 repo 裡真實的東西填滿，不能留下範例或空白：

| 段落 | 回答的問題 |
| --- | --- |
| Launch | 用哪個指令啟動 app？怎麼知道它準備好了？ |
| Doctor | 眼前這個 instance 正常嗎？值得拿來測嗎？ |
| Drive | 怎麼操作它？用 repo 裡真實的按鈕名稱和指令 |
| Evidence | 要留下哪些證據？放在哪裡？ |
| Cleanup | 測完怎麼收拾？ |

Launch 對「準備好了」的定義很嚴格：要能用，而不只是 process 有回應。

Evidence 段落裡寫了幾條證明標準：

- 走使用者真正會走的路，不用內部的 setter 或測試專用的 endpoint。
- 留下動作和動作後的狀態，不能只拍最後一個畫面。
- 除了畫面，也要檢查 side effect：檔案有沒有寫進去、資料有沒有存進資料庫、訊息有沒有送出。
- 用 dry-run 模式時，親自觀察它略過了什麼，不要相信它的名字。有些 dry-run 還是會連網路、開瀏覽器。

Cleanup 則有兩條界線：只關掉這次自己啟動的東西，不能按程式名稱一把全殺；證據要留著，放在 skill 指定的位置。

### feature map：每個功能怎樣算能用

除了驗證 skill，它還會產生一份 feature map。先挑出 3 到 5 個使用者最常用的功能，每個功能一個檔案，固定分成四段：

- 子功能：這個功能包含哪些行為。
- 使用者怎麼到達：每一個入口都要列出來。
- 怎麼操作：每個使用者動作，配上精確的指令和看得到的結果。
- 陷阱：哪些地方會浪費一次驗證，或讓驗證結果不算數。

**feature map 就是這個專案的驗證標準**：每個功能從哪裡進去、做到哪一步、看到什麼才算能用。這些知識原本只存在熟悉專案的人腦袋裡，現在成了任何 agent 都讀得懂的檔案。

### 讓驗證 skill 與時俱進

app 會一直改，feature map 寫好的那一刻就開始過時。pstack 另外有 `/maintain-verification-skill`，guide 建議至少每天跑一次，最好排成自動執行：

1. 每個功能派一個 sub agent 讀 source code，找出 feature map 和實際行為不一致的地方。
2. 把每個功能實際操作一次。就算 source 看起來沒問題，這一步也不能省。
3. 把驗證過的修正整理成一個 PR。沒有要修的，就不開 PR。

### 用起來

有了驗證 skill，「驗證一下」就成了任何 agent 都能照做的步驟：

```text
/poteto-mode 做出批次封存的功能。
用 /verify-<app> 驗證你的修改，
再給我看影片和截圖當證據。
```

## 結語

整套 pstack 提供的不只是那工程工作流，也是一連串建立信任的方式。

回到剛開始的流程：

> 建立規範、磨合出信任 -> 建立驗證機制 -> 擴展到雲端 agent

我自己會用這套哲學優化平常在用的 skill set，也期望大家能有所收穫，在 agent 自動化這路上走得更遠。
